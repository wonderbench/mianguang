# 合成容量与持续运行验收

`benchmark_platform` 在专用 PostgreSQL 演示部署上生成真实 HTTP 请求，覆盖设备接入、人员会话轮询和单绑定24小时趋势/CSV查询。每次运行输出一份 JSON 记录；它不会将短跑、合成数据或容器恢复结果写成真机/机构验收。

已执行的6,000行与6,048,000行短时负载、原始JSON和CI来源见[软件验收记录](../reports/README.md)。常规PR使用6,000行；工作流手动运行可选择6,048,000行。两者的CI混合负载均为30秒，不满足24小时验收。

## 运行条件

- 应用已完成迁移和 `init_roles`，有一个具备平台管理权限的 `--actor` 账号。
- 命令配置必须为 `DEMO_MODE=true`，且数据库中不能存在 `is_simulator=false` 的真实设备。命令与目标 HTTPS 应用必须连接同一个演示数据库。
- 人员来源 IP 在 Nginx 允许网段中；目标返回 `Server-Timing: app;dur=<毫秒>`。使用机构可信证书，内部 CA 可显式提供 `--ca-file`；工具没有跳过证书验证的选项。
- 每次新建自己的模拟场地、设备、绑定与只读账号。正常结束或Python异常退出时，通过 `finally` 尝试停用本批设备、结束绑定、撤销 token、失效临时查看员及会话；观测和审计保留。数据库不可写会明确记录清理未完成；强制终止进程也可能留下本批数据，恢复后重建独立演示库。重复运行不会删除前次历史，因此完整容量试验应从新数据库开始。

在容器外本机运行时，使用 `platform/README.md` 的 PostgreSQL 环境变量。若使用 Compose，可通过 `docker compose exec -e DEMO_MODE=true app ...` 执行；把报告从容器复制出来归档。

## 短跑：验证工具与100台突发

以下示例持续混合负载60秒，并建立6,000条完整合成历史；不是24小时或605万行验收。

```sh
DEMO_MODE=true python app/manage.py benchmark_platform \
  --url https://platform.example.org --actor admin \
  --devices 100 --viewers 10 --duration 60 --seed-rows 6000 \
  --output /tmp/mianguang-capacity-smoke.json
```

仅回环开发地址可使用 `--url http://127.0.0.1:8000 --allow-local-http`。容器内使用临时自签测试证书时，应通过 `--ca-file /tmp/ci-ca.pem` 明确信任该证书，且主机名必须匹配。

工具等待新绑定5秒隔离期，然后让所有设备在同一计划时刻发送一次 HTTPS 请求，记录为 `burst`。这是同时重连时的 **HTTP 请求突发模拟**，不代表实际 Wi-Fi 重连。之后执行错峰混合负载：每设备10秒一包、每查看员会话15秒一次总览片段查询，另一个管理员会话每15秒查询一组24小时趋势与CSV。每台最多一个请求在途，不补发过时快照；调度落后会记录缺失次数并使运行检查失败。

## 完整合成容量验收

按设计候选主机准备足够数据库/WAL/备份空间，固定软件版本并记录实际主机配置，再运行：

```sh
DEMO_MODE=true python app/manage.py benchmark_platform \
  --url https://platform.example.org --actor admin \
  --devices 100 --viewers 10 --duration 86400 --seed-rows 6048000 \
  --require-full --revision <本次部署提交SHA> \
  --output /srv/mianguang-results/capacity-24h.json
```

历史种子使用 PostgreSQL `generate_series`，每设备一批，保留完整 v1 payload、规范化 JSON 的 SHA-256、正确绑定关系和排序水位。100台各60,480个10秒点，总计6,048,000行；历史使用 boot 1，HTTP 新采集使用 boot 2。只为本次新建的模拟绑定回填历史期间，不修改已有业务绑定。种子不通过只接收当前快照的实时接入接口伪装补传。

`duration` 只计持续混合负载，不计建数、绑定隔离、前置突发或最终核对时间。配置允许15秒至24小时，不会把较短时长换算成24小时完成。命令在真实时间持续运行；CI 的短跑仅验证调用链，完整执行需使用可持续运行且资源符合目标的受控主机。

本工具不调用日清理，且完整作业期间不应为这个独立演示库另行运行清理定时器。100台24小时会在6,048,000条种子基础上增加约864,000条周期上报和100条突发记录，达到约6,912,100条；报告同时给出实际计数和数据库字节数。七日保留清理由独立集成/部署检查验证，不用删除载荷字段或缩小真实行大小来代替容量目标。

## 人员会话口径

工具在受控本地数据库中创建标准 Django `SessionStore` 会话，然后通过 HTTP 携带会话 cookie 查询真实受权限控制的页面/API。10个查看员使用10个独立会话，CSV另用一个管理员会话。

这是**会话轮询模拟，不是浏览器渲染或登录端点压测**；报告中 `http_logins=0`。这样不会把登录入口每IP限流混入页面容量测量。会话在配置寿命的一半或6小时（取较短者）续建；默认8小时会话在4小时续建，并删除旧会话。报告记录 `sessions_created` 与 `session_renewals`，因此24小时运行不会因初始会话自然过期而停止模拟值守。

## 报告、门槛与退出码

JSON 分别记录 `burst`、`telemetry`、`overview`、`series`、`csv` 的请求数、HTTP状态/错误计数和响应字节数，核对预期调度次数、每台接受情况、实际入库行数及 latest/排序水位一致性。还记录真实持续时间、种子行数、软件版本、CPU/内存与可读的 cgroup 限额、数据库和观测表含索引的字节数。不会输出 token、Session cookie、连接串或环境变量转储。

- `app_p95_ms` 来自服务端 `Server-Timing`，覆盖 Django 处理/渲染，不包含反向代理排队和网络传输。
- `client_p95_ms` 包含 TLS、网络等待和完整响应接收；不能拿它替代服务端处理时间。
- P95 以1毫秒直方图向上取整，避免为24小时运行保存全部载荷或逐请求浮点列表。每项同时给出样本数与有服务端计时的请求数；缺失计时使运行检查失败。
- `observed_app_thresholds` 对照接入500ms、总览1秒、趋势/CSV各2秒。短跑中的数值仅代表本次样本。
- `full_capacity_passed=true` 要求同时满足100台、10查看会话、实际至少86,400秒、6,048,000条本次历史种子、全部正确性检查和性能目标。即便为true，也不代表真机、真实浏览器、机构无线网络或生产恢复指标已验收。

退出码 `0` 表示所配置运行的正确性检查通过；短跑仍明确标记 `smoke_passed` 和未执行的完整范围。退出码 `1` 表示请求、调度、计时或数据一致性失败。指定 `--require-full` 后，范围不足或性能目标未达成返回 `2`。保留 JSON 报告与同一部署提交的 CI/容器日志，按实际结果填写交付记录。

仍需现场执行的三台真机24小时、UART/灯响应、邻床影响、断电/重新配置，以及机构异机备份和恢复RTO/RPO，按照 [开发验收](development.md) 和 [运行与恢复](operations.md) 单独记录。
