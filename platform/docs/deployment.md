# 最小部署与运维方案

本页为部署设计基线，实际三容器配置与执行步骤见[运行与恢复](operations.md)。尚未部署到机构主机或连接真机。候选配置是一台4 vCPU、8 GiB内存、100 GiB SSD的Linux主机，运行Nginx、Django/Gunicorn、PostgreSQL三个容器；容量是否足够以[压测验收](development.md#5-性能与试点门槛)为准。

## 1. 两类现场共用一个应用

| 场景 | 配置方式 |
|---|---|
| 疗养院同一网络 | 主机可在院内；设备Wi-Fi到服务器443、可信时间源可达；人员浏览器在院内/VPN访问 |
| 社区分散住户 | 一台机构服务器提供可达域名与设备HTTPS入口；设备只主动连接，无需住户路由器端口转发；人员页面限制在机构出口/VPN |

两者不需要不同业务系统。不假定院内Wi-Fi稳定，也不承诺在公网断网时仍有平台观测；现场夜灯必须独立工作。首版不增加常驻USB网关来掩盖固件缺少联网功能。

数据库仅容器私网开放，宿主机不映射5432；应用端口也只允许Nginx访问。设备入口与人员入口是同域名不同路径，在Nginx分别限制网络访问和请求频率；公网开放设备写入口不等于把Admin暴露给所有公网客户端。

TLS使用机构域名的受信任证书，或由机构分发并在设备正确配置根证书的内部CA；必须覆盖实际主机名。内网IP不自动免除证书校验。配置证书续期和设备信任更新的维护过程，P0不做OTA分发根证书。设备UTC准备所用NTP来源与网络权限也要现场核查。

## 2. 权限与数据处理

管理员创建账号、登记设备、改绑定、轮换密钥及导出；查看员只读本部署全部床位和趋势。不提供公开注册、邀请邮件、外部第三方登录或移动端推送；密码恢复由受控管理员/主机运维执行。

启用Django会话、CSRF、模板转义、Secure/HttpOnly Cookie、SameSite=Lax、登录失效和退出；建议会话8小时，退出立即失效。`DEBUG=false`，明确`ALLOWED_HOSTS`、可信代理/TLS转发头、CSRF可信源；设备视图的专用token鉴权不能扩展为全站CSRF关闭。[Django部署清单](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/)、[CSRF说明](https://docs.djangoproject.com/en/5.2/ref/csrf/)

Nginx对设备路由可先用每IP20请求/秒、burst=200的待测配置容纳100台设备共用NAT；登录入口单独使用更低速率并测试多人同网登录。配置`limit_req_status=429`，禁止默认将限流误当服务器故障。用户网络拓扑影响阈值，这些数值是起始配置，不是已验证安全界限。[Nginx限流文档](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)

凭证每台独立32字节随机数，数据库只存摘要；只有管理员完成轮换事务后一次性展示，显示页面`no-store`且不缓存。设备配置文件不进入Git，交付工具默认隐藏token，配置后不原文回读。数据库/备份包含敏感观测，应限制系统账户和存储权限。

机构启用前确认试点对象授权、查看人员范围、保存期限与退出/删除流程；首版只存内部住户代号。该清单是实际部署准备事项，不声明已完成任何监管认证或医疗用途评估。

## 3. 容量与保留

100台 × 8640条/日 = **864,000条/日**；7天约6,048,000条。以每行含索引摊销暂估3 KiB，仅观测数据约2.47 GiB/日、17.3 GiB/7天；实际JSONB、索引、WAL、清理回收和备份大小需实测。100 GiB候选磁盘还须留出数据库膨胀、日志、升级与至少一份恢复空间，不据此承诺容量。

- Observation保留7天；AuditEntry保留90天；过期Session与已结束绑定的过期身份文本每日清理。数据库记录时间戳，不收长期睡眠档案。
- 每天分批删除过期行，避免一次大事务；管理命令使用PostgreSQL advisory lock避免重复清理，清理失败退出非零并写运维日志。正常autovacuum保持开启，观察磁盘实际回收趋势。
- 不再建长期聚合表，详情查询只访问单个绑定的最多24小时数据。长期报告确有需求时再另行定义口径与保留。

## 4. 备份和恢复

每日对PostgreSQL做一致性逻辑备份（`pg_dump`自定义格式），加密后保存到**另一台机构受控主机或既有备份系统**，保留7份日备份；备份加密密钥与备份分开保管。无需为本项目新建对象存储服务。数据库用户、应用密钥、Nginx配置与证书另按机构密钥保管流程备份，密钥不进入Git或普通数据库转储注释。

`pg_dump`的用法依据[PostgreSQL官方说明](https://www.postgresql.org/docs/17/app-pgdump.html)。备份成功必须包括非零退出检查、文件大小/摘要与加密成功；定期在隔离空库恢复并验证账号、Binding、Device水位与观测关联。不能向恢复测试库连接真实设备。

每日备份的目标RPO为24小时，恢复目标RTO为2小时，均需演练证明。7天在线保留叠加7份日备份，已从在线库清理的记录还可能在备份中最多再存约7天；对机构说明最长残留窗口，备份到期删除。删除请求涉及备份时，应按机构确认的恢复后再清除流程处理，不能声称在线删除立即消灭全部副本。

发布前先备份，执行迁移和`manage.py check --deploy`，使用Gunicorn而非开发服务器。镜像回退只适用于兼容迁移；涉及不可逆数据变更时必须按恢复方案操作，不能把“换回旧镜像”当数据库回滚。

## 5. 最少运维可见性

应用结构化日志只含请求ID、内部设备ID、状态码、错误分类和耗时；不记Authorization、完整请求体、住户代号或RR/HR值。记录接入接受/重复/拒绝计数、数据库失败、清理和备份结果；首版通过现有主机日志/定时器日志管理，不搭Prometheus/Grafana整套平台。

`/healthz`仅供容器/运维网检查应用与数据库；它正常不代表所有雷达正常。值守人员查看总览的“无新上报/待现场处理”；本轮不接短信、电话或护理呼叫系统。主机故障会使页面不可用，不能宣称同一个已失效页面仍能通知工作人员。

实际部署交付清单应包含域名/IP、时间源、证书到期、人员角色、设备编号与绑定配置发放记录、备份责任人、恢复演练结果和3台实机试点记录；密钥本体单独保管。当前文档没有自动创建这些资源。
